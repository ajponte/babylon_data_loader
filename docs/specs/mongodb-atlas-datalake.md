# MongoDB Atlas Datalake Specification & Architecture

## 1. Executive Summary

This document specifies the MongoDB Atlas cloud architecture, data models, network security, and credential management powering the **Babylon 2.0 Datalake**. The datalake acts as the durable financial data repository for transaction records ingested by [`babylon_data_loader`](../../README.md) and consumed downstream by [`babylon_features`](../../../babylon_features) and the [`babylon`](../../../babylon) application backend.

```mermaid

        SM[AWS Secrets Manager<br/>babylon/datalake/credentials] -.->|Fetch MONGO_SECRET_ID| Lambda
    end

    subgraph Atlas ["Database Layer (MongoDB Atlas - AWS us-west-2)"]

        Cluster --> Coll2[Collection: transactions_synthetic]
        Cluster --> CollSync[Collection: dataSync]
    end

    subgraph Downstream ["Downstream Consumers"]
        Cluster -.->|Query Datalake| Features[babylon_features<br/>ZenML & Feature Pipelines]
        Cluster -.->|Read Transactions| Backend[babylon<br/>Flask Web Server]
    end
```

## 3. Network Access & Serverless Security Architecture

### 3.1. Serverless Egress Model
The `babylon-data-loader` AWS Lambda function runs in default serverless compute mode outside a dedicated Virtual Private Cloud (VPC). Outbound network traffic from Lambda originates from AWS's regional public IP address pools in `us-west-2`.

To permit inbound connections from Lambda without static IP pinning or expensive NAT Gateways:
- **IP Access List Entry**: `0.0.0.0/0` (`Allow Access from Anywhere`).
- **Entry Description**: `AWS Lambda Serverless Egress`.

### 3.2. Defense-in-Depth Security Controls
Allowing `0.0.0.0/0` is standard for serverless functions and remains secured by:
1. **Transport Layer Encryption**: All traffic is strictly enforced over TLS 1.3 with mandatory certificate verification. Plaintext connections are rejected.
2. **Authentication**: SCRAM-SHA-256 challenge-response authentication with strong, autogenerated database user credentials (`babylon_app`).
3. **Role-Based Access Control (RBAC)**: The database user is restricted strictly to `readWrite` operations on database `datalake`. Administrative privileges (`root`, `clusterAdmin`) are not granted.
4. **Zero-Secret Secrets Manager**: Database credentials are never hardcoded or stored in code repositories. They are dynamically resolved at runtime from AWS Secrets Manager with in-memory caching.

## 4. AWS Secrets Manager Schema & Credential Resolution

### 4.1. Secrets Manager Secret Definition
The datalake credentials are stored in AWS Secrets Manager under secret name `babylon/datalake/credentials` (configured via Terraform in `babylon_deploy/terraform/modules/datalake/main.tf`).

#### Secret Payload Schema:
```json
{
  "engine": "mongodb",
  "host": "<cluster-host>.mongodb.net",
  "port": "27017",
  "username": "babylon_app",
  "password": "<secure-database-password>",
  "database": "datalake",
  "auth_source": "admin",
  "mongo_uri": "mongodb+srv://babylon_app:<secure-database-password>@<cluster-host>.mongodb.net/datalake?retryWrites=true&w=majority"
}
```

### 4.2. Runtime Credential Precedence
As implemented in [`config/secrets.go`](../../config/secrets.go), `GetMongoURI` resolves database connection details following this strict order of precedence:

1. **Local Environment Override (`MONGO_URI`)**: If the `MONGO_URI` environment variable is set, it is returned immediately. This allows developers to point local CLI builds or unit tests to local Docker containers (`mongodb://localhost:27017/datalake`).
2. **Thread-Safe In-Memory Cache**: A `sync.RWMutex` cache stores the resolved URI across warm Lambda invocations, reducing AWS Secrets Manager API costs to zero for warm invocations.
3. **AWS Secrets Manager Resolution (`MONGO_SECRET_ID`)**: On cache miss, the function calls Secrets Manager, parses the JSON payload (or direct URI string), caches the connection string, and returns it.

## 5. Datalake Schema & Collection Partitioning

The `datalake` database organizes financial records into partitioned collections based on the ingestion source and data provider:

### 5.1. Transaction Collections (`transactions_<datasource>`)
Financial transactions are segregated by data source to allow independent schema validation, distinct retention policies, and origin traceability:

| Collection Name | Source / File Format | Description |
| :--- | :--- | :--- |
| **`transactions_chase`** | `Chase*_Activity_*.CSV` | Checking, savings, and credit card statements from Chase Bank |
| **`transactions_synthetic`** | Synthetic generator CSVs | Test transaction datasets generated for QA without real PII |
| **`transactions_<custom>`** | Future statement formats | Dynamic collections created based on detected file header extractors |

#### Transaction Document Structure:
```json
{
  "_id": "67104b2b8c9d123456789abc",
  "accountId": "6896",
  "postingDate": "2023-03-12T00:00:00Z",
  "description": "GROCERY STORE PURCHASE",
  "amount": -45.67,
  "transactionType": "DEBIT",
  "balance": 1250.34,
  "category": "Groceries",
  "rawDetails": "PURCHASE AUTHORIZED ON 03/11 GROCERY STORE #1234",
  "sourceFile": "Chase6896_Activity_20230312.CSV",
  "importedAt": "2026-10-17T01:41:08Z"
}
```

### 5.2. Ingestion Audit Collection (`dataSync`)
Tracks synchronization logs for every file processed by the loader engine to enforce deduplication and trace lineage:

```json
{
  "_id": "67104b2b8c9d123456789abd",
  "fileName": "Chase6896_Activity_20230312.CSV",
  "fileHash": "283d4493dc4e0ed154928aed2a9dbe8f25f5add70f220bfdc0d624c0af8f9834",
  "recordCount": 93,
  "upsertedCount": 93,
  "matchedCount": 0,
  "status": "SUCCESS",
  "syncedAt": "2026-10-17T01:41:08Z",
  "durationMs": 983
}
```

## 6. Verification & Operational Tooling

### 6.1. Inspecting Live Data via `mongosh`
To query the datalake directly from your terminal using the Atlas connection string:

```bash
# List all datalake collections
mongosh "<mongo-uri>" --eval "db.getCollectionNames()"

# Inspect record counts across collections
mongosh "<mongo-uri>" --eval "
  print('transactions_chase:', db.transactions_chase.countDocuments());
  print('transactions_synthetic:', db.transactions_synthetic.countDocuments());
  print('dataSync logs:', db.dataSync.countDocuments());
"

# Inspect latest sync record
mongosh "<mongo-uri>" --eval "db.dataSync.find().sort({syncedAt: -1}).limit(1)"
```
